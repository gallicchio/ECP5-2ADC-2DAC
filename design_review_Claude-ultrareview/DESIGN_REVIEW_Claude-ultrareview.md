## Reasoning, verbatim

### 1. `gen/fpga.py`

build/fpga_pins.json is not checked into this repo (unlike build/netlist.net, build/lcsc.json, build/placement.json, etc., which are), so it must be regenerated by running `python3 gen/fpga.py`, and `gen/gen.py`, `pcb/pinswap.py`, `pcb/build_pcb.py` (via river/pinswap), `gen/lpf.py`, and `mfg/make_fab.py` all `import fpga` or `import fpga as F` transitively. Because `BALLS = load()` executes at module import (gen/fpga.py:68) and `load()` opens `CSV` unconditionally (gen/fpga.py:33), any of these entry points -- including the documented top-level `python3 build.py` pipeline -- fails immediately with FileNotFoundError on a fresh clone of this repo, before any pin assignment, schematic generation, PCB build, or manufacturing output can be produced.

**Verification:** normal. gen/fpga.py:24 sets `CSV = os.path.join(HERE, "..", "datasheets", "FPGA-SC-02033-2-0-ECP5U-25-Pinout.csv")` with HERE = the gen/ dir, so it resolves to `ECP5-2ADC-2DAC/datasheets/FPGA-SC-02033-2-0-ECP5U-25-Pinout.csv`. No `ECP5-2ADC-2DAC/datasheets/` directory exists (datasheets live under `ECP5-2ADC-2DAC/docs/datasheets`, which contains no CSV), and the only copy of that pinout file in the repo is in the sibling project `IcepiZeroADCDAC/datasheets/`.

### 2. `pcb/build_pcb.py`

self.rf (build_pcb.py:114) is the set of net names on pin 1 of the analog SMA jacks J301/J302/J101/J102/J204/J205, and RF_W=0.35mm (line 51) is the hand-computed 50-ohm microstrip width for exactly those nets. The retry-pass helper width_of() (lines 957-963) checks `if n in self.rf: return RF_W` before anything else, but the FIRST pass at lines 948-954 computes `width = CLASS_WIDTH.get(net_class(net), 0.15)` with no self.rf check at all. Because these SMA-side signal segments are frequently auto-named (e.g. J301 pin 1's net is literally "Net-(C5421-Pad1)" in build/netlist.net, not an AIN_/AOUT_-labelled name), net_class() falls through rules.PATTERNS to "Default", giving width=0.15mm (CLASS_WIDTH["Default"]) instead of the required 0.35mm RF_W -- nearly a 60% under-width controlled-impedance trace. Since the SMA-to-front-end run is short and uncongested, it is very likely to route successfully in this very first attempt and therefore never reach the retry loop that would have used width_of() and the correct RF_W.

**Verification:** normal. self.rf (build_pcb.py:114) is the set of pin-1 nets of J301/J302/J101/J102/J204/J205, and RF_W=0.35 (line 51) is the intended 50-ohm microstrip width for them (comment line 113). The retry-pass helper width_of() checks self.rf FIRST (lines 957-959: `if n in self.rf: return RF_W`), proving the design intends these nets to be routed at 0.35mm. But the FIRST routing pass (lines 948-954) computes `width = CLASS_WIDTH.get(net_class(net), 0.15)` with no self.rf check.

### 3. `build.py`

Running python3 build.py produces a step-5/9 log entry that drops all the per-river and per-pool summaries (lane counts, vias, balls moved, clearance problems, pool lengths) and shows only the trailing "wrote build/pin_swaps.json (...)" line, so anyone reading the build log (or CI) loses visibility into whether a bus river had clearance problems or how many pins moved, making a real pinout regression easy to miss until DRC or pad-check fails later. Likely a leftover from renaming the "bank" terminology to "pool" without updating this filter.

**Verification:** nit. build.py:143 filters pinswap.py stdout with `if l.startswith("bank") or l.startswith("wrote")`, but every print() in pcb/pinswap.py emits lines beginning with `river ` (line 79), `    CLEARANCE` (line 82), `pool ` (lines 122/149), `pinswap: pool ` (line 126), or `wrote ` (line 155) — none start with "bank". The dead "bank" predicate means the step-5/9 summary shows only the final `wrote ...` line and drops all per-river/per-pool detail (lane counts, vias, balls moved, clearance problems). The step title at line 141 still reads "per bank", confirming a leftover rename.

### 4. `mfg/end_panels.py`

The comment says labels should be "staggered on two rows" (above/below), but the `or True` forces every label to be placed above the cutout (only the 3.0*(k%2) horizontal/vertical offset still varies); the intended lower-row placement in the else branch can never execute, leaving confusing, unreachable code in mfg/end_panels.py that a future edit (e.g. removing the stray `or True`) would silently change the rendered end-panel SVG/DXF label layout.

**Verification:** nit — At ECP5-2ADC-2DAC/mfg/end_panels.py:85 the ternary condition is `k % 2 == 0 or True`, which is unconditionally True. By Python's conditional-expression precedence the whole line parses as `(v + h/2 + 2.0 + 3.0*(k%2)) if (k % 2 == 0 or True) else (v - h/2 - 2.5)`, so the else branch `v - h/2 - 2.5` (label placed below the cutout) is genuinely unreachable. The claim is factually correct: labels are always placed above, with the only variation being the `3.0 * (k % 2)` stagger. The stray `or True` is dead code a future edit could silently change.

### 5. `gen/lpf.py`

No behavioral bug today since the branch is a true no-op, but it reads as if clock pins get special IOBUF handling (e.g. a pull config) when they get none, which will mislead the next person editing gen/lpf.py into believing clock-pin IOBUF options are already handled here when they add a real one; cost is wasted investigation time and risk of silently losing the intended distinction if someone 'simplifies' nearby code assuming this branch does something. Fix: delete the dead branch (lines 50-51), or if clock pins were meant to get a specific IOBUF option, implement it.

**Verification:** nit — quality finding, factually true. gen/lpf.py line 49 sets `extra = ""`, then lines 50-51 `if n.startswith("clk_") or n == "eth_rxc": extra = ""` reassign the identical value. Nothing else between them touches `extra`, so the branch is a pure no-op. The only meaningful assignment is the unrelated PULLMODE=UP case on lines 52-53, which never matches clock pins. The branch does read as if clock pins receive special IOBUF handling when they receive none, which could mislead a future editor. Deleting lines 50-51 changes no output.

### 6. `pcb/place.py`

No functional impact, but these are vestigial functions (place.py:234-235's identity function `x2_`, fpga.py:235-248's `_lvds_pairs`) left over from an earlier approach; they cost a reader time figuring out whether they are load-bearing, and `_lvds_pairs` in particular duplicates/precedes the hand-picked GPDI pairing logic now done inline in `assign()`, so keeping both invites the two to drift apart if someone edits one believing the other calls it. Fix: delete both, which covers the 2 sites listed.

**Verification:** nit (quality/cleanup, does not block merge).
